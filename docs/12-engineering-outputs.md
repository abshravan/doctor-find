# Phase 12 — Engineering Outputs

> Implementation playbook for DoctorFind: API design, repo/monorepo setup, Docker, CI/CD,
> deployment, Kubernetes, observability, logging, and analytics. This document maps 1:1 to the
> code scaffold in this repository (`apps/api`, `docker-compose.yml`, `.github/workflows/ci.yml`).

---

## 1. Guiding principles

1. **Modular monolith first.** One deployable FastAPI app with clean internal module boundaries
   (`agents/`, `api/routers/`, `models/`, `services/`). Extract services only when a real scaling
   or team-ownership reason appears. See `docs/03-system-architecture.md`.
2. **Deterministic core, agentic edges.** Money/availability/booking paths are plain code. LLMs
   live at the conversational edges (intake, triage navigation, receptionist). See `docs/04`.
3. **Safe-by-default.** Emergency detection and disclaimers are enforced in code, not left to the
   model. The scaffold's `app/agents/triage.py` checks red-flags *before* any LLM call.
4. **Boring infra early.** Single VM or PaaS (Railway/Render/Fly) + managed Postgres + Redis.
   Kubernetes is a Phase-2 concern, documented but not adopted on day 1.

## 3. API design

REST + JSON, OpenAPI auto-generated by FastAPI at `/docs`. Conventions:

- Versioning via prefix: `/api/v1/...` (omit in the scaffold for brevity; add a router prefix).
- Auth: `Authorization: Bearer <jwt>`; phone-OTP login (MSG91) issues access + refresh tokens.
- Errors: RFC-7807-ish `{ "detail": "...", "code": "..." }`. 4xx for client, 5xx for server.
- Idempotency: `Idempotency-Key` header on `POST /appointments` (dedupe double-taps).
- Pagination: cursor or `page`/`page_size` (scaffold uses the latter).

### Representative endpoints (implemented in scaffold)

```
GET  /health                         # liveness
POST /triage                         # AI Symptom Navigator -> urgency/specialty/consult-type
GET  /doctors?specialty=&city=&...   # discovery + filters
POST /appointments                   # booking (RBAC: appointment:create)
```

### Endpoint contract example — triage

```http
POST /triage
Content-Type: application/json

{ "message": "severe chest pain since morning", "language": "en" }
```
```json
{
  "session_id": "f1c2...",
  "reply": "This sounds like it may be a medical emergency...",
  "urgency": "emergency",
  "recommended_specialty": "Emergency Medicine",
  "consultation_type": "offline",
  "is_emergency": true,
  "disclaimer": "I'm an AI navigator, not a doctor... call 112..."
}
```

### FastAPI endpoint pattern (from the scaffold)

```python
@router.post("/appointments", response_model=BookingOut, status_code=201)
async def create_appointment(
    payload: BookingRequest,
    db: AsyncSession = Depends(get_db),
    principal: dict = Depends(require("appointment:create")),  # RBAC
):
    appt = Appointment(patient_id=principal["sub"], **payload.model_dump())
    db.add(appt); await db.commit(); await db.refresh(appt)
    # emit event -> async confirmation + reminder workflow
    return appt
```

## 4. Event-driven architecture & queues

Bookings, reminders, notifications, and call summaries are **async**. Keep it simple at MVP:

```
HTTP request ──► write DB ──► publish event (Redis Stream) ──► consumer
                                                              ├─ WhatsApp confirm (Gupshup)
                                                              ├─ schedule reminder (Temporal)
                                                              └─ analytics sink
```

**Event taxonomy (examples):**
`appointment.requested`, `appointment.confirmed`, `appointment.cancelled`,
`reminder.due`, `call.completed`, `triage.completed`.

**Queue choice by stage:**

| Need | MVP | Scale |
|------|-----|-------|
| Fire-and-forget jobs | Redis + Celery/RQ | Kafka consumers |
| Durable, multi-step, retried workflows (reminders, follow-ups, missed-call callbacks) | **Temporal** (worth it early — booking reminders are timers that must not be lost) | Temporal (HA) |
| Ops glue (CRM sync, sheets, email) | n8n | n8n / Airflow |

**Why Temporal early:** "remind 24h and 2h before the appointment, retry WhatsApp then fall back
to a voice call, stop if cancelled" is exactly a durable workflow. Cron + DB polling is the
simpler alternative if you want to defer Temporal — start there if team bandwidth is tight.

### Temporal workflow pseudocode — appointment reminders

```python
@workflow.defn
class AppointmentReminderWorkflow:
    @workflow.run
    async def run(self, appt_id: str, scheduled_at: datetime):
        await workflow.sleep_until(scheduled_at - timedelta(hours=24))
        if await is_cancelled(appt_id): return
        await send_whatsapp_reminder(appt_id)            # activity, auto-retried
        await workflow.sleep_until(scheduled_at - timedelta(hours=2))
        if await is_cancelled(appt_id): return
        ok = await send_whatsapp_reminder(appt_id)
        if not ok:
            await place_reminder_call(appt_id)           # voice fallback (docs/06)
```

## 5. Caching strategy

| Cache | What | TTL | Invalidation |
|-------|------|-----|--------------|
| Redis | Doctor search results (hot specialty+city combos) | 60–300s | on profile/availability write |
| Redis | Specialty list, cities, config | 1h | manual/version bump |
| Redis | Session/conversation state (triage) | 30m sliding | on session end |
| Redis | OTP + rate-limit counters | 5m / sliding | TTL |
| CDN | Web SSG/ISR discovery pages, doctor profile images | ISR revalidate | on update |
| App | LLM response cache for identical low-risk prompts | 24h | hash(prompt+model) |

Cache-aside pattern. Never cache PII-bearing payloads without encryption + short TTL.

## 6. Docker setup

`docker-compose.yml` (root) boots `db` (pgvector/pgvector:pg16), `redis`, and `api`. The API
`Dockerfile` (`apps/api/Dockerfile`) installs deps first for layer caching, then copies source.

```bash
cp .env.example .env
docker compose up --build      # http://localhost:8000/docs
```

Production image hardening checklist: pin base image digest, run as non-root user, multi-stage
build (builder + slim runtime), `--no-cache-dir`, healthcheck, read-only FS where possible.

## 7. CI/CD pipeline

`.github/workflows/ci.yml` runs lint (ruff) + tests (pytest) on every push/PR for `apps/api`.

**Pipeline stages (target):**

```
push ─► lint (ruff, mypy) ─► unit tests (pytest) ─► build image
      ─► integration tests (compose: api+db+redis) ─► security scan (trivy, pip-audit)
      ─► push image (GHCR) ─► deploy staging ─► smoke test ─► manual gate ─► deploy prod
```

- Per-app jobs (path filters) so web/mobile/api build independently.
- Migrations run as a pre-deploy step (`alembic upgrade head`) with a rollback plan.
- Tag images with git SHA; deploy by SHA for instant rollback.

**Deploy strategy by stage:**

| Stage | Platform | Why |
|-------|----------|-----|
| MVP (0–10k MAU) | Render/Railway/Fly + managed Postgres + Upstash Redis | zero ops, fast |
| Growth | AWS ECS/Fargate or GCP Cloud Run + RDS + ElastiCache | managed scaling |
| Scale | Kubernetes (EKS/GKE) | multi-service, fine-grained scaling |

## 8. Kubernetes (Phase 2 — document, don't prematurely adopt)

When you outgrow PaaS:

```
infra/k8s/
├── api-deployment.yaml        # HPA on CPU + RPS; readiness=/health
├── worker-deployment.yaml     # Temporal workers (separate scaling)
├── voice-gateway.yaml         # WebRTC/SIP bridge (sticky, autoscaled on calls)
├── ingress.yaml               # nginx/ALB + cert-manager TLS
├── secrets (External Secrets Operator -> AWS Secrets Manager)
└── hpa.yaml
```

Guidelines: separate deployments for **api**, **workers**, and **voice gateway** (very different
scaling profiles — voice is latency- and connection-bound). Use HPA on RPS/concurrent-calls, not
just CPU. Postgres stays managed (RDS/Cloud SQL), not in-cluster.

## 9. Observability stack

| Concern | Tool (MVP) | Tool (Scale) |
|---------|-----------|--------------|
| Metrics | Prometheus + Grafana (or Grafana Cloud free) | Same, HA |
| Tracing | OpenTelemetry SDK → Tempo/Jaeger | OTel → vendor (Honeycomb/Datadog) |
| Logs | structured JSON → Loki | Loki / OpenSearch |
| Errors | Sentry | Sentry |
| Uptime | BetterStack/UptimeRobot | Same |

Instrument FastAPI with `opentelemetry-instrumentation-fastapi`. **AI-specific telemetry is
non-negotiable:** log every LLM call's prompt hash, model, tokens, latency, cost, tool calls,
and safety-filter outcomes (route to Langfuse/Phoenix for LLM tracing + eval). See `docs/04`
evaluation metrics: triage routing accuracy, escalation recall, containment rate, hallucination
rate, p95 latency.

**Golden signals to alert on:** API p95 latency, 5xx rate, booking success rate, **emergency
escalation recall** (synthetic canary calls), voice call drop rate, LLM error/timeout rate, daily
AI spend.

## 10. Logging stack

- Structured JSON logs (`structlog`), one line per request with `request_id`, `user_id` (hashed),
  `route`, `latency_ms`, `status`.
- **PII discipline (docs/07):** never log raw phone numbers, symptoms, or transcripts at INFO.
  Mask/redact; store sensitive conversation content only in the encrypted `ai_messages` /
  `voice_transcripts` tables with retention policies and consent flags.
- Correlation: propagate `request_id` → events → workflows → voice calls for end-to-end tracing.

| Layer | Tool | Use |

| Product analytics | PostHog (self-host or cloud) | funnels: triage→discovery→booking, retention |
| Warehouse | Postgres read-replica → BigQuery (later) | reporting, cohort analysis |

## 13. Technical-debt warnings (read before you "just ship it")

- **Don't** put the LLM in the booking/payment critical path — keep those deterministic.
- **Don't** store transcripts/symptoms without encryption, consent, and retention — DPDP risk.
- **Don't** skip the Idempotency-Key on bookings — double-booking is a trust-killer.
- **Don't** adopt microservices/k8s before you have the load or the team. The modular monolith
  here is intentional.
- **Do** keep the emergency-escalation path covered by tests + synthetic canaries from day 1
  (see `apps/api/tests/test_triage.py`).
- **Do** generate typed API clients from OpenAPI for web/mobile to avoid contract drift.
